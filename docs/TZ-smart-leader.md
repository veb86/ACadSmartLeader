# ТЗ: умная выноска ACadSmartLeader

**Проект:** ACadSmartLeader. Это выноска AutoCAD, которая читает XDATA объекта, на котором стоит её стрелка,
и выводит значения на полки.
**Основание:** [задача #1](https://github.com/veb86/ACadSmartLeader/issues/1).
**Смежный проект:** [acadPaletteSetXDATA](https://github.com/veb86/acadPaletteSetXDATA). Он задаёт объектам
параметры (XDATA `BobrovXDATA` v2, схема в NOD `VELEC`). Документ проверен по его состоянию на тег `v0.0.143`.
**Платформа:** AutoCAD 2021 (`net48`, основная), AutoCAD 2024 (`net48`), AutoCAD 2025+ (`net8.0-windows`).
Язык — C#, интерфейс — WPF. Поставка — одна DLL `ACadSmartLeader.dll` в пакете Autoloader (`.bundle`).

Документ описывает, **что** делать и **в каком порядке**. Код выноски в рамках задачи #1 не пишется.
В репозиторий добавлены только проверочные эксперименты (`experiments/`) и пример правил подписей (`examples/`).

---

## 1. Цель

В чертеже уже есть информационная модель: у объектов (двигатели, кабели, лотки, устройства) есть параметры в XDATA.
Выноска должна показывать эти параметры, а не текст, набранный вручную.

1. Пользователь ставит выноску так, чтобы стрелка лежала на объекте (линия кабеля, блок двигателя).
2. Выноска определяет этот объект, читает его XDATA и выводит значения на полки по настраиваемому правилу.
   Пример для двигателя: верхняя полка — позиция, нижняя — мощность. Пример для кабеля: группа.
3. Когда меняются данные объекта (например, мощность двигателя), команда `SL_UPDATE` перечитывает значения
   во всех выносках. Также можно включить автоматическое обновление по `REGEN`/`REGENALL`.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Выноска | Объект AutoCAD `MLeader` (мультивыноска) с данными ACadSmartLeader в XDATA (раздел 7). |
| Цель | Объект чертежа, на котором стоит стрелка выноски; его XDATA выводится на полки. |
| Полка | Строка текста выноски. Верхняя полка — над линией, нижняя — под линией. |
| Правило подписи | Именованная настройка: к каким объектам применяется и что выводится на каждую полку (раздел 8). |
| Формат | Строка с подстановками `@@[Id]` или формула `=…`. Синтаксис — `CalculatedString` из acadPaletteSetXDATA. |
| Обновление | Повторное чтение XDATA цели и пересчёт текста полок. |
| Отвязанная выноска | Выноска, у которой цель не найдена или стрелка с неё ушла (раздел 9.4). |
| Core | Платформенно-независимая часть acadPaletteSetXDATA (`AcadPaletteSetXData.Core`, `netstandard2.0`). |

## 3. Анализ запроса

### 3.1. Что из задачи однозначно

- Источник данных — XDATA, которые записывает acadPaletteSetXDATA. Это формат `BobrovXDATA` v2
  (`docs/xdata-v2.md` того проекта): пары `Id` → значение, шаблон `TEMPLATE`, `DEVICE_ID`. Схема параметров
  (названия, типы, справочники, точность) хранится в NOD `VELEC`.
- Цель определяется положением стрелки: стрелка «стоит на линии данного объекта».
- На выноске две полки (верхняя и нижняя). Их содержимое настраивается.
- Есть явное обновление командой `SL_UPDATE`. Его можно связать с `REGENALL`.

### 3.2. Пробелы и решения этого ТЗ

| Пробел | Решение |
| --- | --- |
| Чем является выноска: стандартный объект или свой класс? | Стандартный `MLeader` с MText из двух строк (раздел 6). Без плагина он виден, печатается и редактируется как обычная выноска. |
| Где хранить, какой объект — цель? | В XDATA выноски: handle цели (код 1005) и `DEVICE_ID` (раздел 7). |
| Где хранить настройку «что выводить»? | Правила подписей лежат в NOD чертежа и импортируются/экспортируются в JSON (раздел 8). Правило выбирается по шаблону цели. |
| Каким синтаксисом задавать вывод? | Синтаксисом `CalculatedString` (`@@[Power] кВт`, формулы `=…`). Вычисляет его тот же Core, что и палитра. Справочники, точность и `Да/Нет` выводятся одинаково (раздел 10). |
| Что такое «позиция» двигателя? | В примере схемы (`examples/schema.json`) нет параметра «Позиция». По умолчанию используется `Device_Number` («Номер»). Шаблон `MOTOR` нужно дополнить этим параметром (раздел 19). |
| Что считать «стоит на линии»? | Расстояние от точки стрелки до геометрии объекта не больше допуска (раздел 9.2). |
| Что делать, если стрелку передвинули на другой объект? | При обновлении выноска перепривязывается к объекту под стрелкой (раздел 9.3). |
| Что делать, если цель удалена? | Выноска становится отвязанной: текст сохраняется и помечается, пользователь получает отчёт (раздел 9.4). |
| Что, если пользователь отредактировал текст вручную? | Это обнаруживается по сохранённому тексту. Ручной текст не затирается без подтверждения (раздел 11.4). |
| Можно ли отменить обновление? | Да. Обновление — одна транзакция и один шаг Undo (раздел 11.3). |
| Как обновлять при `REGENALL`? | Подписка на `CommandEnded` с `REGEN`/`REGENALL`. Режим включается настройкой (раздел 11.2). |

## 4. Выбор языка: C#

| Критерий | C# (.NET API) | C++ (ObjectARX) |
| --- | --- | --- |
| Повторное использование acadPaletteSetXDATA | Подключается Core: разбор `BobrovXDATA` v2, `SchemaCache`, `CalculatedString`/NCalc. Формат читается тем же кодом, что пишет палитра. | Парсер XDATA v2, схемы NOD, справочников и формул (NCalc) пришлось бы писать заново на C++ и поддерживать синхронно с C#-версией. |
| Объекты и события, нужные выноске | `MLeader`, `Curve.GetClosestPointTo`, XDATA, NOD, `Database.ObjectModified/Erased`, `DeepCloneEnded`, `Document.CommandEnded`, Overrule. Наличие проверено по сборкам API 24.0.0 (приложение А). | Всё то же есть, плюс собственные классы объектов. |
| Собственный класс объекта (custom entity) | Недоступен. | Доступен. Но без Object Enabler на другом компьютере объект виден как proxy. Для выноски это недостаток, а не преимущество. |
| Собственное вычисляемое поле (Field evaluator) | Недоступно. В сборках .NET API есть только служебный `Internal.FieldEngine` (приложение А). | Доступно. Но это не нужно: обновление по команде решает задачу без полей. |
| Интерфейс (диалог правил, предпросмотр) | WPF, как в палитре; общий стиль и тема. | MFC/Win32 или отдельный слой. |
| Сборка и CI | NuGet `AutoCAD.NET` (reference assemblies), `dotnet build` на GitHub Actions, тесты Core без AutoCAD. Так уже работает acadPaletteSetXDATA. | ObjectARX SDK для каждой серии AutoCAD, Visual Studio с нужным toolset, отдельные сборки под 2021/2024/2025. Публичного NuGet-пакета нет. |
| Совместимость версий | Одна `net48` DLL для 2021–2024, отдельная `net8.0-windows` для 2025+. | Отдельный бинарник на каждую серию (R24.0, R24.3, R25…). |
| Производительность | Достаточная: обновляются сотни–тысячи выносок за одну транзакцию (раздел 14). | Выше, но здесь не узкое место. |

**Решение: C#.** Возможности C++ (собственный класс объекта, собственное поле) задаче не нужны и только ухудшают
переносимость чертежа. Главное — совместимость с acadPaletteSetXDATA: выноска должна понимать XDATA и схему ровно
так же, как палитра. C# даёт это повторным использованием Core, а не второй реализацией формата.

C++ стоит рассмотреть заново, только если появится требование, недостижимое в .NET API. Например, выноска,
которая пересчитывается без плагина. Сейчас такого требования нет (раздел 19).

│   └── TargetGeometry       — допуски и выбор цели по расстояниям (раздел 9), без типов AutoCAD
├── AutoCAD
│   ├── Commands             — команды (раздел 12)
│   ├── LeaderFactory        — создание MLeader, текст, стиль, слой

### 5.1. Связь с acadPaletteSetXDATA

- Исходники Core acadPaletteSetXDATA подключаются как git submodule, закреплённый на теге. Они компилируются
  в `ACadSmartLeader.dll` так же, как это делает сам `acadPaletteSetXDATA.csproj` (Core-исходники
  компилируются в одну DLL, NCalc встраивается ресурсом и подгружается `EmbeddedAssemblies`).
  Отдельного пакета Core нет. Ссылаться на `acadPaletteSetXDATA.dll` из выноски нельзя: модули загружаются
  независимо, и выноска должна работать без палитры.
- Используемые API Core:
  - `XDataV2.Read(EntityDataSnapshot, SchemaSnapshot)` → `ObjectValues`;
  - `ObjectCalculation(ObjectValues, CultureInfo)` и `.Text(id)`, `.Find(id).IsError`, `.Find(id).Error`;
  - `SchemaCache`, `SchemaSnapshot`, `ParameterSchemaJson.Clone`.
  - Чтение XDATA объекта в `EntityDataSnapshot` нужно повторить по образцу `AutoCadDataReader.ReadEntity`.
    Этот файл в слое AutoCAD, его можно подключить тем же submodule.
- Вместе с палитрой в одном AutoCAD загружаются две DLL с одинаковыми классами Core в разных сборках.
  Конфликта нет: сборки разные, и типы не передаются между модулями. Версия встроенного NCalc должна совпадать
  (`[7.4.0]`). Иначе первый загруженный обработчик `AssemblyResolve` подсунет другой версии. Проверяется
  тестом «оба модуля загружены» (этап 1).
- Желательно, но не обязательно: добавить в Core acadPaletteSetXDATA публичный метод вычисления произвольного
  формата для объекта, например `ObjectCalculation.Evaluate(string format)`. До этого выноска использует
  проверенный обходной путь (раздел 10.1).
- Свой корень NOD (`VELEC_LEADER`), а не запись внутри `VELEC`. Неизвестные записи в `VELEC` палитра читает
  с предупреждением, поэтому смешивать их нельзя.

## 6. Представление выноски на чертеже

### 6.1. Объект

Выноска — стандартный `MLeader` с `ContentType = MTextContent`:

- одна линия выноски со стрелкой. Точка стрелки определяет цель. Линия идёт от стрелки сразу к полке;
- полка (`EnableLanding = true`, `EnableDogleg = true`);
- текст MText из двух абзацев: `верх\Pниз`;
- `TextAttachmentType = AttachmentBottomOfTopLine` (значение 6, в интерфейсе — «Подчеркнуть верхнюю строку»).
  Полка проходит между верхней и нижней строкой, текст над линией и под ней — «верхняя полка» и «нижняя полка».
  Прикрепление задаётся для левой и правой стороны (`SetTextAttachmentType(…, LeaderDirectionType.LeftLeader/RightLeader)`).
- если правило задаёт только одну полку, текст однострочный, `AttachmentBottomLine` («Подчеркнуть нижнюю строку»).

Без загруженного плагина такая выноска остаётся обычной мультивыноской: показывается, печатается, копируется
в другие чертежи, правится стандартными ручками и командами. Плагин нужен только для создания и обновления.

### 6.2. Внешний вид

- Размер текста, стрелка, отступы берутся из стиля мультивыноски `MLeaderStyle`, указанного в правиле.
  Если стиль не указан — текущий стиль чертежа (`CMLEADERSTYLE`).
- Слой — из правила. Если слой не указан — текущий слой.
- Длина полки — по ширине более длинной из двух строк. Это поведение AutoCAD при подчёркивании; проверяется
  на прототипе (раздел 18).
- Аннотативность и масштабы — как у выбранного стиля. Плагин их не меняет.

### 6.3. Рассмотренные варианты (не выбраны)

| Вариант | Почему не выбран |
| --- | --- |
| Собственный класс объекта (C++ custom entity) | Нужен Object Enabler, без него proxy. Нужен C++ (раздел 4). |
| `MLeader` с блоком и атрибутами `TOP`/`BOTTOM` | Нужен блок в каждом чертеже. Длина полки не подстраивается под текст без динамического блока. Можно добавить позже как вариант правила (раздел 19). |
| Поле (Field) в MText со ссылкой на объект | Стандартные поля не читают XDATA. Собственное поле — только в C++. |
| Отрисовка текста через `DrawableOverrule` | Без плагина текста не видно, при печати и экспорте в PDF без плагина тоже. |

## 7. Данные выноски (XDATA)

RegApp `BobrovLeader`. Формат — пары «ключ (1000) → значение». Он похож на `BobrovXDATA` v2, но это отдельный
RegApp: палитра не должна принимать выноску за объект информационной модели.

| Ключ | Код значения | Обязательно | Значение |
| --- | --- | --- | --- |
| — | `(1070 . 1)` | да | Версия формата, сразу после `(1001 . "BobrovLeader")`. |
| `TARGET` | 1005 | да* | Handle цели. При копировании вместе с целью AutoCAD переводит handle на копию (раздел 18). |
| `TARGET_ID` | 1000 | нет | `DEVICE_ID` цели (GUID). Запасной способ найти цель после `WBLOCK`/`INSERT`, если handle не переведён. |
| `RULE` | 1000 | да | Id правила подписи (раздел 8). Пусто — правило выбирается автоматически по шаблону цели. |
| `TOP` | 1000 | нет | Формат верхней полки этой выноски вместо формата правила. |
| `BOTTOM` | 1000 | нет | Формат нижней полки этой выноски вместо формата правила. |
| `TEXT` | 1000 | да | Текст, записанный в MText при последнем обновлении. По нему обнаруживается ручная правка (раздел 11.4). Если текст длиннее 255 байт, хранится хэш SHA-1 с префиксом `#`. |
| `STATE` | 1070 | да | 0 — привязана; 1 — отвязана (цель не найдена); 2 — ошибка формата; 3 — ручной текст. |

\* `TARGET` пуст только у отвязанной выноски.

Ограничения те же, что у `BobrovXDATA`: строка до 255 байт, общий объём XDATA объекта до 16 КБ.
Форматы длиннее 255 байт задаются только в правиле, не в выноске.

## 8. Правила подписей (настройка вывода)

### 8.1. Модель

```json
{
  "format": "ACadSmartLeader.labels",
  "version": 1,
  "rules": [
    {
      "id": "MOTOR",
      "caption": "Двигатель: номер / мощность",
      "templates": [ "MOTOR" ],
      "entityTypes": [ "BlockReference" ],
      "top": "@@[Device_Number]",
      "bottom": "@@[Power] кВт",
      "empty": "—",
      "style": "Смарт-выноска",
      "layer": "Выноски"
    }
  ]
}
```

| Поле | Обязательно | Значение |
| --- | --- | --- |
| `id` | да | Уникальный идентификатор (латиница, цифры, `_`). Ссылка из XDATA выноски. |
| `caption` | да | Название в интерфейсе. |
| `templates` | нет | Шаблоны схемы (`TEMPLATE` объекта), к которым правило подходит автоматически. |
| `entityTypes` | нет | Типы объектов, как в шаблонах схемы (`Line`, `Polyline`, `BlockReference`, …). |
| `top`, `bottom` | хотя бы одно | Форматы полок (раздел 10). Пустая или отсутствующая полка не выводится. |
| `empty` | нет | Текст для полки, у которой все подстановки пусты. По умолчанию пусто. |
| `error` | нет | Текст при ошибке формата. По умолчанию `#ОШИБКА`, как в палитре. |
| `style` | нет | Имя стиля мультивыноски. Если стиля нет в чертеже — текущий стиль и предупреждение. |
| `layer` | нет | Слой новой выноски. Если слоя нет — создаётся. |

Полный пример с правилами для двигателя, кабеля и лотка — [`examples/label-rules.json`](../examples/label-rules.json).

### 8.2. Выбор правила

1. Если в выноске задан `RULE` и такое правило есть — оно.
2. Иначе первое правило, у которого `templates` содержит шаблон цели, а `entityTypes` пуст или содержит тип цели.
3. Иначе первое правило без `templates`, подходящее по `entityTypes`.
4. Иначе правило не найдено: выноска не создаётся, пользователю показывается, для какого шаблона нет правила.

### 8.3. Хранение

- В чертеже: NOD `VELEC_LEADER` → словарь `LABELS` → один Xrecord на правило (ключ — `id`), поля «имя + значение».
  Так же устроена схема в `VELEC` у acadPaletteSetXDATA (`docs/schema-nod.md`): один объект — один Xrecord.
  Порядок правил хранится полем `order`.
- Команды импорта/экспорта JSON (раздел 12). При импорте JSON проверяется (раздел 8.4); при ошибках он
  не записывается.
- Если правил в чертеже нет, используется файл по умолчанию рядом с DLL (`label-rules.json` в `.bundle`).
  Он копируется в чертёж при первом создании выноски. Так правила переносятся вместе с чертежом.

### 8.4. Проверки правил

- `id` уникальны и не пусты, есть `top` или `bottom`.
- Форматы разбираются Core. Ошибки синтаксиса (`незакрытая ссылка @@[`) и неизвестные `Id` схемы показываются
  при импорте и в диалоге как предупреждения. Правило с такими ошибками сохраняется: схема может измениться позже.
- Неизвестные поля JSON сохраняются и выводятся предупреждением (расширяемость, как у схемы).

## 9. Привязка к цели

### 9.1. При создании

1. Пользователь указывает точку стрелки (`GetPoint` с объектной привязкой; рекомендуется привязка «Ближайшая»).
2. Под точкой ищутся объекты с XDATA `BobrovXDATA`: выбор `SelectCrossingWindow` вокруг точки с размером
   допуска, фильтр по RegApp. Если в этой точке нет объекта с данными, предлагается выбрать объект вручную
   (`GetEntity`). Тогда стрелка переносится в ближайшую точку выбранного объекта.
3. Из найденных выбирается ближайший по расстоянию (раздел 9.2). При равенстве побеждает объект выше
   в порядке прорисовки.
4. Выбирается правило (раздел 8.2), вычисляются полки, пользователь указывает место полки (`GetPoint`
   с предпросмотром текста). `MLeader` создаётся с данными раздела 7.

### 9.2. «Стрелка стоит на объекте»

Расстояние `d` от точки стрелки `P` до объекта:

- `Curve` (отрезок, полилиния, дуга, сплайн): `|P − GetClosestPointTo(P, false)|` в плоскости объекта;
- `BlockReference`: минимум по кривым определения блока, преобразованным `BlockTransform`
  (вложенные блоки — рекурсивно, до глубины 4). Если кривых нет — расстояние до `GeometricExtents`
  (внутри рамки — 0);
- прочие объекты — по `GeometricExtents`.

Стрелка стоит на объекте, если `d ≤ tolerance`. По умолчанию `tolerance` равен 1 % высоты текста стиля выноски,
но не меньше `1e-6` единиц чертежа. Настраивается. Вычисление расстояний и выбор ближайшего — в
`TargetGeometry` Core: так это покрывается тестами без AutoCAD.

### 9.3. При обновлении

1. Цель по `TARGET`: `Database.TryGetObjectId(handle)`. Объект существует, не удалён, и стрелка стоит
   на нём (9.2) → цель та же.
2. Иначе ищется объект `BobrovXDATA` под стрелкой (9.1, шаг 2). Найден → выноска перепривязывается,
   в отчёте «перепривязана: был X, стал Y». Это же исправляет копию выноски без цели и выноску, стрелку
   которой передвинули ручкой.
3. Иначе цель по `TARGET_ID` (`DEVICE_ID`) среди объектов чертежа. Найдена → handle обновляется,
   но стрелка не двигается, в отчёте предупреждение «стрелка не на объекте».
4. Иначе выноска отвязана (9.4).

### 9.4. Отвязанная выноска

- Текст не меняется (последние значения остаются видимыми). `STATE = 1`.
- В отчёте обновления: список отвязанных выносок; их можно выбрать командой (раздел 12).
- Визуальная пометка не меняет чертёж. Отвязанные выноски подсвечиваются при выборе в отчёте.
  Цвет и текст не меняются: иначе при печати получится «грязный» чертёж.

## 10. Вычисление текста полок

### 10.1. Алгоритм

1. Получить `SchemaSnapshot` чертежа (кэш по документу, сбрасывается при изменении NOD `VELEC`, как в палитре).
2. Прочитать XDATA цели в `EntityDataSnapshot` → `XDataV2.Read` → `ObjectValues`.
3. Пока в Core нет `Evaluate(format)`: склонировать схему (`ParameterSchemaJson.Clone`) и добавить в неё
   форматы правил как вычисляемые параметры `CalculatedString` со служебными Id
   (`__LEADER_<rule>_TOP`/`_BOTTOM`). Отсутствующая полка в схему не добавляется: пустой формат Core считает
   ошибкой («не задан format»). Клон строится один раз на снимок схемы и набор правил, не на каждую выноску.
   Затем `new ObjectCalculation(values, culture).Text(id)`.
4. Если `Find(id).IsError` — текст полки = `error` правила, причина ошибки — в отчёт. Core в строковом режиме
   при ошибке оставляет ссылку как есть (`@@[Unknown_Id]`), это проверено. Выноска сама заменяет такой текст
   на `#ОШИБКА`, чтобы ошибка была заметна.
5. Если все подстановки пусты (значения нет ни в XDATA, ни по умолчанию) — текст полки = `empty` правила.
6. Экранирование MText: `\`, `{`, `}` в значениях экранируются; две полки соединяются `\P`.

Подход проверен экспериментом [`experiments/LabelFormatCheck`](../experiments/LabelFormatCheck/Program.cs)
без AutoCAD. Он берёт настоящий Core acadPaletteSetXDATA (`v0.0.143`), его `examples/schema.json` и правила
из [`examples/label-rules.json`](../examples/label-rules.json) этого репозитория.
Вывод сохранён в [`output.txt`](../experiments/LabelFormatCheck/output.txt):

| Правило (шаблон) | Формат верх / низ | Результат |
| --- | --- | --- |
| MOTOR | `@@[Device_Number]` / `@@[Power] кВт` | `М1` / `7,50 кВт` (точность 2 из схемы) |
| MOTOR_FULL | `@@[GC_Name]` / `=@@[Power] & ' кВт, ' & @@[Current] & ' А'` | `ЩУ1.3` / `7,50 кВт, 15,2 А` |
| CABLE | `@@[GC_Name]` / `@@[Cable_Mark] @@[Cable_Cores]x@@[Cable_Section]` | `ЩУ1.3` / `ВВГнг-LS 5x2,5` |
| CABLE_GROUP | `@@[GC_Name]` / — | `ЩУ1.3` / нижней полки нет |
| ANY (MOTOR) | `@@[Device_Type]` / `@@[NMO_Name]` | `Электродвигатель` (значение по умолчанию шаблона) / `Насос подпитки` |
| ANY (CABLE) | то же | пусто / пусто → выводится `empty` правила |
| ошибочное | `@@[Unknown_Id]` / `@@[Cable_Mark` | ошибки «неизвестная ссылка», «незакрытая ссылка @@[» |
| MOTOR после изменения `Power` на 11 | `@@[Power] кВт` | `11,00 кВт` |

Запуск из папки `experiments/LabelFormatCheck` (клон acadPaletteSetXDATA лежит в `<repo>`):
`dotnet run -p:XDataRepo=<repo> -- <repo> [путь к правилам]`. Путь к правилам по умолчанию —
`../../examples/label-rules.json`.

### 10.2. Синтаксис формата

Тот же, что у `CalculatedString` (`docs/calculated-string.md` acadPaletteSetXDATA):

- строковый режим: `@@[Id]` — значение (для справочника — подпись), `@@[Id:key]` — ключ справочника,
  `@@@@` — символ `@@`;
- режим формулы: формат начинается с `=`, выражение NCalc, ссылки `@@[Id]`, склейка `&`, `IF`, `ROUND` и т. д.;
- числа выводятся с точностью из схемы (`editor.precision`) и десятичным разделителем культуры; логические — `Да`/`Нет`.

Расширение (этап 5): свойства самой цели — `@@[$Layer]`, `@@[$Length]` (длина кривой с точностью из настроек),
`@@[$Handle]`. Это служебные Id выноски, они подставляются до передачи формата в Core.

## 11. Обновление

### 11.1. Ручное обновление

- Команда `SL_UPDATE`. Если перед ней выбраны выноски (PickFirst) — обновляются они. Иначе запрос
  «Обновить [Все/Выбрать] <Все>». «Все» — все выноски `BobrovLeader` в пространстве модели и во всех листах.
- Для каждой выноски: найти цель (9.3), выбрать правило (8.2), вычислить текст (10), сравнить с MText.
  Записывать только изменившиеся выноски. Неизменённые не открываются на запись, Undo и `DBMOD` не трогаются.
- Итог в командной строке: «Выносок: N, изменено: X, без изменений: Y, перепривязано: Z, отвязано: U, ошибок: E».
  Если есть отвязанные или ошибки — предложение выбрать их (`SL_SELECT_PROBLEMS`).

### 11.2. Обновление по `REGEN`/`REGENALL`

- Настройка `UpdateOnRegen` = `Off | Regen | RegenAll` (по умолчанию `RegenAll`). Хранится в настройках
  пользователя (как настройки палитры) и меняется командой `SL_SETTINGS`.
- Реализация: подписка на `Document.CommandEnded`. Если `GlobalCommandName` — `REGENALL` (или `REGEN` при
  `UpdateOnRegen = Regen`), в `Application.Idle` ставится однократный запуск
  `SendStringToExecute("_SL_UPDATE _All ", …)`. Так обновление идёт отдельной командой:
  у неё своя транзакция, своя запись Undo, нет записи в базу изнутри обработчика события.
- Защита от повторного входа: `SL_UPDATE` сам не вызывает `REGEN`/`REGENALL`. Пока выполняется запланированное
  обновление, флаг документа отключает реакцию на `CommandEnded`.
- Вызов `REGENALL` из LISP/скриптов тоже ловится через `CommandEnded`. Проверяется на прототипе (раздел 18).

### 11.3. Транзакция и Undo

- Все выноски одного запуска меняются в одной транзакции. Отмена (`U`) возвращает весь запуск.
- Заблокированные слои: такие выноски пропускаются и попадают в отчёт. Слой не разблокируется.
- Выноски во внешних ссылках (xref) не обновляются (только для чтения).

### 11.4. Ручная правка текста

Если текст MText не совпадает с `TEXT` из XDATA, значит, пользователь правил текст вручную.

- `SL_UPDATE` без ключей не затирает такие выноски, а отмечает их в отчёте (`STATE = 3`).
- Ключ `_Force` обновляет их тоже.
- Команда `SL_EDIT` позволяет вместо ручной правки задать в выноске собственный формат `TOP`/`BOTTOM`.

### 11.5. Автоматическое обновление при изменении цели (этап 5, по умолчанию выключено)

- `Database.ObjectModified` по объектам с `BobrovXDATA`: отметить изменённые handle. По `CommandEnded`
  запланировать обновление выносок, которые на них ссылаются (индекс «цель → выноски», раздел 14).
- По умолчанию выключено: предусмотрены `SL_UPDATE` и `REGENALL`, а автоматика усложняет Undo
  (изменения выносок становятся отдельным шагом после команды пользователя).

## 12. Команды и интерфейс

| Команда | Действие |
| --- | --- |
| `SL_CREATE` | Создать выноску (9.1). Ключи: `_Rule` — выбрать правило вручную. |
| `SL_CREATE_GROUP` | Создать отдельную выноску по правилу с суффиксом `_GROUP`. |
| `SL_UPDATE` | Обновить выбранные или все выноски (11.1). Ключи `_All`, `_Select`, `_Force`. |
| `SL_EDIT` | Диалог выбранной выноски: правило, свои форматы `TOP`/`BOTTOM`, предпросмотр, «Перепривязать» (указать новую цель). |
| `SL_RULES` | Диалог правил чертежа: список, редактирование, предпросмотр на выбранном объекте, кнопка «Вставить параметр» (список параметров схемы → `@@[Id]`). |
| `SL_RULES_IMPORT` / `SL_RULES_EXPORT` | Импорт/экспорт JSON правил (8.3). |
| `SL_SELECT_PROBLEMS` | Выбрать отвязанные, ошибочные и вручную изменённые выноски. |
| `SL_SETTINGS` | Режим `UpdateOnRegen`, допуск привязки. |

- Префикс `SL_` выбран, чтобы не пересекаться с командами палитры (`VELEC_*`, `XDATAPALETTE`).
- Команды запускаются из командной строки AutoCAD. Будущая интеграция описана в [ТЗ на кнопки меню](TZ-autocad-menu.md).
- Диалоги WPF; тема и стиль как у палитры.

## 13. Особые случаи

| Ситуация | Поведение |
| --- | --- |
| `COPY` выноски вместе с целью | Handle `TARGET` переводится на копию цели (проверить, раздел 18). Если не переводится, при обновлении срабатывает 9.3 п. 2: стрелка копии стоит на копии цели. |
| `COPY` только выноски | `TARGET` указывает на старую цель, но стрелка на ней не стоит → 9.3 п. 2/4. |
| `MOVE`/`STRETCH` цели без выноски | Стрелка уходит с объекта. При обновлении — предупреждение или отвязка (9.3). Выноска сама не двигается. |
| `WBLOCK`/`INSERT`/вставка из буфера | Handle может не сохраниться → поиск по `TARGET_ID`, затем по стрелке. |
| Цель удалена | Отвязка (9.4). После `U` (отмены удаления) следующее обновление снова находит цель по handle. |
| Цель без `BobrovXDATA` (данные стёрли) | Полки получают `empty`. В отчёте «у цели нет данных». |
| Шаблон цели изменился | Правило выбирается заново, если в выноске `RULE` пуст. |
| В чертеже нет схемы `VELEC` | Значения выводятся как есть (строки, числа без точности). Предупреждение один раз за запуск. |
| Схема изменилась (импорт, редактор) | Кэш схемы сбрасывается, следующее обновление использует новую схему. |
| Цель — объект во вложенном блоке или xref | Не поддерживается на этапах 1–4: выбирается вставка блока целиком. Решение по умолчанию в разделе 19. |
| Несколько документов | Кэши и подписки — по документу. Подписки снимаются при закрытии документа. |
| Плагин не загружен | Выноска остаётся обычной мультивыноской с последним текстом. |
| Выноска разбита `EXPLODE` | Становится текстом и линиями без данных. Это ожидаемо. |
| Пространство листа и видовые экраны | Выноска на листе со стрелкой на объекте модели через видовой экран — не поддерживается (раздел 19). Выноска и цель должны быть в одном пространстве. |

## 14. Производительность

- Обновление 1000 выносок — не дольше 2 с на типовом компьютере. Транзакция одна; MText меняется только
  при изменении текста.
- Объекты-цели читаются по одному разу на запуск, даже если на один объект указывает много выносок.
- Схема и клон схемы с форматами правил (10.1) кэшируются по документу.
- Индекс «цель → выноски» строится при первом обновлении и поддерживается событиями
  `ObjectAppended`/`ObjectErased`. Он нужен только для автоматического режима 11.5.
- Поиск под стрелкой (`SelectCrossingWindow`) работает только по видимой области экрана. Для выносок вне экрана
  применяется перебор пространства с предварительным отбором по `GeometricExtents`.

## 17. Этапы реализации

### Этап 1. Каркас и создание выноски

- Проект, submodule Core, CI, пакет `.bundle`.
- `SL_CREATE` с правилами из `label-rules.json` по умолчанию; XDATA выноски (7); вычисление полок (10).
- **Приёмка:** на двигателе с `Power = 7.5` создаётся выноска «М1» над полкой и «7,50 кВт» под полкой;
  на кабеле — «ЩУ1.3» / «ВВГнг-LS 5x2,5». Без плагина чертёж открывается, выноска видна. Тесты Core проходят в CI.

### Этап 2. Обновление

- `SL_UPDATE`, отчёт, Undo, ручная правка (11.1, 11.3, 11.4), перепривязка и отвязка (9.3, 9.4).
- **Приёмка:** изменить мощность двигателя в палитре на 11 → `SL_UPDATE` → у всех выносок двигателя «11,00 кВт».
  `U` возвращает «7,50 кВт». Удалённая цель даёт отвязанную выноску в отчёте. Скопированная вместе с целью
  выноска показывает данные копии.

### Этап 3. `REGEN`/`REGENALL` и настройки

- 11.2, `SL_SETTINGS`.
- **Приёмка:** при `UpdateOnRegen = RegenAll` команда `REGENALL` обновляет все выноски одним шагом Undo.
  При `Off` — не обновляет. Нет повторного входа и зацикливания.

### Этап 4. Правила в чертеже и диалоги

- NOD `VELEC_LEADER`, `SL_RULES`, `SL_RULES_IMPORT/EXPORT`, `SL_EDIT` с предпросмотром и вставкой параметров.
- **Приёмка:** правило, изменённое в диалоге, сохраняется в чертеже и действует после повторного открытия.
  Экспорт → импорт в другой чертёж даёт те же правила. Ошибка формата видна в предпросмотре.

### Этап 5. Расширения

- Свойства цели `@@[$…]` (10.2), автоматическое обновление (11.5), выноска с блоком и атрибутами (6.3),
  несколько стрелок на одной выноске (по разным объектам, полки — объединение значений через `Merge`).
- **Приёмка:** по отдельным задачам.

| Что проверить | Как | Если не подтвердится |

## 19. Открытые вопросы к заказчику (приняты решения по умолчанию)

| Вопрос | Решение по умолчанию |
| --- | --- |
| Что такое «позиция» двигателя, какой параметр? | `Device_Number` («Номер»). Добавить его в шаблон `MOTOR` схемы. Правило легко поменять на `@@[GC_Name]`. |
| Что выводить у кабеля, одну полку или две? | Верх — группа `@@[GC_Name]`, низ — марка и сечение. В правиле можно оставить только верх. |
| Обновление по `REGEN` или только `REGENALL`? | Только `REGENALL` (`UpdateOnRegen = RegenAll`); `REGEN` — настройкой. |
| Нужно ли автоматическое обновление сразу после изменения данных? | Нет, этап 5 и выключено по умолчанию. |
| Должна ли выноска пересчитываться без плагина? | Нет: без плагина выноска хранит последний текст. Иначе нужен C++ (собственное поле или объект), раздел 4. |
| Затирать ли ручной текст при обновлении? | Нет, только с ключом `_Force`. |
| Выноска на листе со стрелкой на объекте модели | Не поддерживается. |
| Цель во вложенном блоке или xref | Выбирается вставка верхнего уровня. Вложенные объекты — отдельной задачей. |
| Где хранить правила: чертёж или общий файл? | В чертеже (NOD) с импортом/экспортом JSON; файл по умолчанию — в `.bundle`. |
| Имена команд и RegApp | `SL_*`, `BobrovLeader`, `VELEC_LEADER` — константы, легко поменять до выпуска этапа 1. |

## Приложение А. Проверенные факты API AutoCAD

Проверено по метаданным сборок NuGet `AutoCAD.NET` 24.0.0 (`AcDbMgd.dll`, `AcCoreMgd.dll`, `AcMgd.dll`)
программой [`experiments/AcadApiProbe`](../experiments/AcadApiProbe/Program.cs). Она читает метаданные
ECMA-335 и не загружает и не выполняет код AutoCAD.

- `TextAttachmentType`: `AttachmentTopOfTop = 0`, `AttachmentMiddleOfTop = 1`, `AttachmentMiddle = 2`,
  `AttachmentMiddleOfBottom = 3`, `AttachmentBottomOfBottom = 4`, `AttachmentBottomLine = 5`,
  `AttachmentBottomOfTopLine = 6`, `AttachmentBottomOfTop = 7`, `AttachmentAllLine = 8`,
  `AttachmentCenter = 9`, `AttachmentLinedCenter = 10`.

  `LandingGap`, `ExtendLeaderToText`, `MLeaderStyle`, `BlockContentId`; методы `AddLeaderLine`,
  `SetTextAttachmentType`, `GetBlockAttribute`/`SetBlockAttribute`, `GetContentGeomExtents`, `PostMLeaderToDb`.

  `WblockEnded`, `InsertEnded`; метод `TryGetObjectId`.
